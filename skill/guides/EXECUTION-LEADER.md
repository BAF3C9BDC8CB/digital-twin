# 执行效率：Leader 工作流

## 核心理念

**你是指挥官，不是士兵。**

不再亲自写代码、不再一个任务接一个任务手动执行。你的角色是：

| 旧角色（工人） | 新角色（Leader） |
|---------------|-----------------|
| 自己动手实现 | 规划拆分，分派任务 |
| 逐个任务执行 | 并行调度多个 sub-agent |
| 陷入细节 | 把控方向和质量 |
| 亲自 debug | 审查结果，指挥修复 |

---

## 工作流程总览

```text
用户需求
    │
    ▼
┌─────────────────────────┐
│ Phase 1: 规划与拆解      │  你来做：理解需求、拆解任务、定义接口
│ 输出: 计划 + todo list   │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ Phase 2: 并行分派        │  你指挥：同时派出多个 sub-agent
│ 输出: 各 sub-agent 结果  │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ Phase 2.5: 逐项验收      │  你验收：亲自跑测试、审查代码质量
│ 输出: 通过/打回 判定     │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ Phase 3: 审查与集成      │  你审查：合并代码、集成测试、最终验收
│ 输出: 可交付的完成品     │
└─────────────────────────┘
```

---

## Phase 1：规划与拆解

### 1.1 理解需求

与用户沟通，明确：
- 做什么（范围）
- 不做什麼（边界）
- 依赖关系（哪些任务必须先完成）
- 技术栈和约定

### 1.2 拆解为独立任务

将工作拆分为**可并行执行**的原子任务。每个任务必须满足：

- **独立**：不依赖其他任务的中间产物
- **有明确边界**：清楚的文件范围、输入/输出
- **可验证**：有明确的完成标准（测试通过 / 构建成功）
- **大小适中**：单个 sub-agent 能在合理时间内完成

> **依赖处理**：如果任务 A 必须等任务 B 完成才能开始，有两种策略：
> 1. **定义接口先行**：先约定好接口/契约，A/B 基于接口并行开发
> 2. **串行依赖**：无法解耦的依赖，分阶段串行执行

### 1.3 定义接口契约

对于需要协作的任务，先锁定接口：

```text
// 任务 A 产出接口 → 任务 B 消费
interface ServiceXInterface {
    methodA(input: Type): OutputType
}
```

双方基于同一接口开发，完成后集成验证。

### 1.4 创建 TodoWrite

```text
□ Phase 2-1: sub-agent 实现 user 模块
□ Phase 2-2: sub-agent 实现 order 模块
□ Phase 2-3: sub-agent 实现 payment 模块
□ Phase 3:   集成测试 + 审查
```

## Phase 2：并行分派

### 2.1 分派原则

- **一个 sub-agent 负责一个任务**，不 overlapping
- **提供完整上下文**：相关文件路径、接口定义、代码风格示例
- **明确输出要求**：完成标准、测试要求、commit 规范
- **不共享文件**：不同 sub-agent 不修改同一文件（防止冲突）

### 2.2 Sub-agent Prompt 模板

```markdown
## 任务: [任务名]

### 上下文
- 项目位置: /data/myProject/xxx
- 相关文件: src/module/xxx.ts, tests/xxx.test.ts
- 需要了解的代码: src/shared/types.ts (类型定义)
- 分支: feature/xxx (已创建)

### 需求
[清晰描述需要实现什么]

### 接口契约
[如果有接口定义，贴在这里]

### 完成标准
1. [ ] 单元测试通过
2. [ ] 测试覆盖新增代码的关键路径（正常流程 + 边界情况 + 错误处理）
3. [ ] 构建通过
4. [ ] commit 到 feature/xxx 分支
5. [ ] 返回 commit SHA、变更摘要、**测试命令和测试结果截图/日志**

### 约束
- 不要修改 src/shared/ 下的文件
- 遵循项目已有的错误处理模式
- 提交前运行 npm run lint

### 测试要求
- 为新增的每个功能点**先写测试，再实现代码**
- 覆盖：正常路径、边界条件、错误/异常输入
- 运行 `npm test` 或对应测试框架命令，确保全部通过
- 返回时附上**测试命令和运行结果**（截图或日志摘要）
```

### 2.3 并行派发

一次性派出所有独立 sub-agent：

```text
→ sub-agent A: 实现 user CRUD
→ sub-agent B: 实现 order CRUD       (同时进行)
→ sub-agent C: 实现 payment 对接
```

等待所有 sub-agent 返回结果。

### 2.4 处理 Sub-agent 问题

| 状态 | 处理方式 |
|------|---------|
| DONE | 记录结果，进入审查 |
| NEEDS_CONTEXT | 补充上下文后重新派出 |
| BLOCKED | 评估阻塞原因：任务太大？拆解再派。缺信息？补充后重试。 |
| DONE_WITH_CONCERNS | 阅读顾虑，判断是否影响合并 |

## Phase 2.5：逐项验收

每个 sub-agent 返回后，**你亲自验收**，不能信任 sub-agent 自述的"测试通过"——你需要亲自跑一遍验证。

### 2.5.1 验收清单

```markdown
□ 代码审查：实现是否合理？有无明显 bug？
□ 测试运行：亲自运行 sub-agent 提供的测试命令，确认通过
□ 测试覆盖：测试是否覆盖了关键路径？还是只测了 Happy Path？
□ 边界情况：sub-agent 是否处理了空值/异常/极限输入？
□ 侵入检查：sub-agent 是否修改了约定范围之外的文件？
```

### 2.5.2 验收命令

```bash
# 切到 sub-agent 的分支
git checkout feature/xxx-A

# 运行测试
npm test                     # Node.js
pytest tests/                # Python
mvn test                     # Java
cargo test                   # Rust

# 构建验证
npm run build                # Node.js
go build ./...               # Go

# 检查改动范围
git diff main --name-only    # 确认只修改了约定文件
```

### 2.5.3 验收不通过处理

| 问题 | 处理方式 |
|------|---------|
| 测试失败 | 记录失败信息，派 sub-agent 修复，重新验收 |
| 测试覆盖不足 | 要求 sub-agent 补充测试用例 |
| 修改了约定外文件 | 要求 sub-agent 撤销多余修改 |
| 实现不符合需求 | 明确差距，派 sub-agent 修正 |

> **原则**：验收不通过 = 打回重做。不要自己动手修 sub-agent 的代码。

## Phase 3：审查与集成

### 3.1 逐项审查

每个 sub-agent 返回后，检查：

- **完整性**：是否按要求完成所有步骤？
- **代码质量**：是否符合项目风格？有无明显的设计缺陷？
- **测试覆盖**：测试是否通过？覆盖了关键路径？
- **安全性**：涉及认证/加密/输入验证的，用 Warp 安全审查

### 3.2 集成验证

所有 sub-agent 完成后：

```bash
# 1. 合并所有分支
git merge feature/xxx-A
git merge feature/xxx-B

# 2. 运行全量测试
npm test

# 3. 构建验证
npm run build
```

### 3.3 冲突处理

如果 sub-agent 修改了相同文件导致冲突：

1. 查看冲突范围
2. 如果只是行级别冲突，手动解决
3. 如果逻辑冲突，派出一个 sub-agent 专门处理合并：
   ```markdown
   ## 任务: 解决合并冲突
   - 文件: src/module/xxx.ts
   - 冲突: A 添加了 validate()，B 重构了 process()
   - 要求: 保留两者功能，确保所有测试通过
   ```

### 3.4 全量审查

集成通过后，进行最终审查：

- **功能完整性**：所有需求是否都已实现
- **回归风险**：改动是否影响现有功能
- **性能考量**：有无明显的性能问题
- **安全审计**：涉及敏感操作的使用 Warp

### 3.5 最终验收

全量审查通过后，进行最终验收。这一步是交付前的**最后关卡**：

```bash
# 1. 运行全量测试套件
npm test                    # 或对应框架命令

# 2. 构建
npm run build / go build / mvn package

# 3. 交付物检查
git log --oneline -10       # 确认提交历史清晰
git diff main --stat        # 确认变更范围可控
```

#### 验收通过标准

| 检查项 | 要求 |
|--------|------|
| ✅ 全量测试 | 全部通过，无 skipped/failed |
| ✅ 构建 | 构建成功，无 warning |
| ✅ 无侵入 | 只修改了约定的文件 |
| ✅ 功能覆盖 | 所有需求可验证 |
| ✅ 安全 | 涉及敏感操作的已通过 Warp 审查 |

> **全部通过** → 交付给用户确认。
> **任何一项不通过** → 回溯到对应 Phase 修复，不得跳过。

## 与现有 Skills 的关系

| Skill | 关系 |
|-------|------|
| **dispatching-parallel-agents** | 本工作流将其升级为正式流程，加入规划-执行-审查三阶段 |
| **subagent-driven-development** | 适用于串行任务；本工作流适用于并行任务，两者互补 |
| **writing-plans** | 本工作流吸收其规划思想，但拆解角度是"并行度"而非"粒度" |
| **executing-plans** | 本工作流取代手写计划文件 + 逐条执行的模式 |

## 使用时机

**使用本工作流当：**
- 任务包含 3 个以上独立模块
- 涉及前后端/多服务同时开发
- 有明确的可并行拆解空间
- 需求相对明确，不需要反复探索

**不使用本工作流当：**
- 简单任务（修改 1-2 个文件）
- 探索性/研究性工作（需要先调查再决定方案）
- 紧密耦合的修改（无法拆分为独立任务）
