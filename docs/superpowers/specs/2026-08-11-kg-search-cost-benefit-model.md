# KG 搜索成本/收益决策模型（成本收益模型 + 决策矩阵 + 预算规则）

- 日期: 2026-08-11
- 角色: 知识图谱搜索成本/收益决策设计
- 关联: `docs/superpowers/specs/2026-08-11-kg-auto-query-strategy.md`（三层漏斗 L0/L1/L2 + 注入预算）、`docs/superpowers/specs/2026-08-11-hermes-kg-integration-plan.md`（§5 搜索时机决策 = 本文件）、`references/kg-query-strategy.md`（实测数据）
- 核心问题: 不是每次都搜最省钱。需要量化"搜索的收益 vs 成本"，给出可执行决策：什么任务搜、什么任务不搜、什么任务浅搜。

---

## 0. 成本的真实计量单位：不是钱，是 context 重放

deepseek-v4-flash 单价极低（一次 search_kg 2.5K raw 约 $0.0004），**钱的成本可忽略**。真实成本是：

1. **context 占用**：KG 结果进入上下文后，挤占有效注意力窗口 → 提前触发压缩轮换 → 每次压缩 = 信息丢失 = 隐性错误风险。
2. **字节稳定重放放大**（实测语义）：注入内容 turn 内每次 API 往返都完整重放（典型 agent turn 3-12 次工具调用 = 3-12 次重放）；结束后历史行持久残留 2-5 个后续 turn 直到压缩轮换。

**真实边际成本 = raw tokens × 重放放大倍数 m（保守 5× / 典型 10× / 最坏 20×）。**

| 注入内容 | raw | effective (m=10) | 备注 |
|---|---|---|---|
| 状态行摘要（project/status/last_build/degraded） | 50-100 | 0.5-1K | 每轮注入的形态 |
| 简报注入（1KB 模板） | 300-500 | 3-5K | 每会话首轮一次 |
| search_kg 裁剪转述（top-3, 字段白名单） | ~500 | ~5K | **推荐的 L1 注入形态** |
| search_kg 原始输出注入（7.2KB） | 2.2-2.5K | 22-25K | 禁止——等于 10 次裁剪版 |
| dt search limit=10（~14KB） | 4-5K | 40-50K | 禁止用于注入 |

> **结论 1：裁剪是唯一的成本杠杆。** 同一次 search_kg，裁剪转述 effective 5K vs 原始注入 25K——5 倍差距，且裁剪还顺带消除噪音误导。预算规则的核心执行点 = 注入时强制裁剪。

## 1. 收益模型：搜索避免了什么

收益 = 搜索避免的失败代价（未发生的 rework/错误/重复查证）。以 effective tokens + 用户时间计量：

| 失败模式 | 触发场景 | 单次代价 |
|---|---|---|
| E 事实错误 | 凭记忆答服务名/端口/URL/凭据/路径 | 5-20K effective + 用户纠正 3-10 min（1 轮纠正 + agent 重查 3-8 次工具调用） |
| R 返工 | 改错目标服务/配置文件/环境 | 10-50K effective + 30 min-数小时 |
| V 乱查 | 违背"先查 KG"原则，用 grep/find/curl 手工乱查 | 8-40K effective（2-4 次工具输出同样被重放放大），且字符串匹配命中率低于语义检索 |
| D 决策污染 | 错误结论被 dt_memorize 入库 | **乘性**：污染后续所有相关任务，上限不可量化 |
| U 用户介入 | 明显违背明示原则被用户打断 | 最贵：整轮上下文作废 + 信任损耗 |

**收益估算公式**：`E[收益] = P(凭记忆会错) × 错误代价 × P(搜索能避免)`。示例（T1 事实查询）：P(错)≈30-50%，代价≈10K，P(避免)≈80% → E[收益]≈3-4K effective + 用户时间；成本（裁剪后）≈5K。**纯 token 视角打平略亏，但用户时间 + 信任 + 自动入库收益使净收益为正** —— 这正是"事实类任务默认搜"的依据：决策偏置不能只看 token。

## 2. 成本量化对比：注入简报 vs 一次 search_kg

| 维度 | 简报注入（1KB, 每会话一次） | 一次 search_kg（裁剪转述） | 一次 search_kg（原始注入） |
|---|---|---|---|
| raw | 300-500 tok | ~500 tok | 2.2-2.5K tok |
| 延迟 | 17-36ms | 1.4s | 1.4s |
| effective（m=10） | 3-5K | ~5K | 22-25K |
| 是否重放放大 | 是，但只注入一次 + 状态行每轮 50-100 | 是，turn 内每次往返带 | 是，且体积 5 倍 |
| 信息量 | 项目级全貌 | 实体级命中 top-3 | 全字段（含噪音） |
| 结论 | **强制层，每任务一次，成本可接受** | **按需层，可接受** | **禁止注入** |

> **结论 2：简报注入 ≈ 裁剪版 search_kg 的成本，但覆盖整个任务的信息底座 → 强制 L0 成立。** 原始 search_kg 注入 = 简报的 5-7 倍 effective 成本，无对应收益（噪音字段不增加决策价值），必须裁剪。

## 3. 决策矩阵：任务类型 × 命中率 × 新鲜度 → 搜/浅搜/不搜

**动作定义**：
- **搜** = `dt_search_kg(query, limit=5)`，注入时裁剪转述 top-3（title/entity_type/snippet/hop/关键属性）
- **搜+** = search_kg + L2 定向 Cypher（字段白名单）——关键属性必须精确确认时
- **浅搜** = 仅 sense（简报已在上下文中，不额外查询）
- **不搜** = 不查 KG，直接干活

**主矩阵：任务类型 × KG 命中率**（命中率 = 索引状态 × 关键词明确度 × 历史命中表现）：

| 任务类型（例子） | H1 命中率高（indexed + 明确词） | H2 命中率中（未索引/词模糊） | H3 命中率低（未注册/宽泛词） |
|---|---|---|---|
| **T1 事实查询**（端口/hostname/URL/凭据/路径） | 搜（hop=0 当事实） | 搜（结果当线索，空则降磁盘验证） | 浅搜 + 明示"KG 未收录，磁盘验证" |
| **T2 变更执行**（改配置/部署/重启服务） | 搜+（关键属性 L2 白名单确认） | 搜+（关键值必须源验证，禁盲改） | 浅搜 + 磁盘直查当前配置（禁止盲改） |
| **T3 历史决策回顾**（为什么这么设计/上次怎么定的） | 搜 | 搜（hop≥1 只当线索） | 浅搜（明示"KG 无决策记录"） |
| **T4 排障诊断**（服务挂了/连接失败） | 搜 | 搜（degraded 时先 dt_health） | 浅搜 + 读日志/当前配置 |
| **T5 纯代码开发**（写/改函数、重构） | 浅搜（简报已覆盖） | 浅搜 | 浅搜 |
| **T6 项目探索/新任务**（不了解项目） | 浅搜（简报即交付物） | 浅搜 | 浅搜（简报含候选注册建议） |
| **T7 机械/文书/闲聊**（格式化/总结/元对话） | 不搜 | 不搜 | 不搜 |

**新鲜度修正（F1 新鲜 ≤1h / F2 中等 ≤1d / F3 陈旧 >1d 或 degraded）**：
- **F3 + T1/T2**：搜索照做，但结果标注 `⚠ stale`，关键值（端口/凭据/路径）必须经源验证（当前配置/磁盘），**等效命中率降一档**（H1→H2，H2→H3）。
- **F1 + 本会话刚写**（dt_memorize/dt_build/jcli_build 后）：缓存强制失效，重查保证新鲜。
- **degraded**：一律降为浅搜 + 注入 `⚠ KG degraded: [...]`，不 search_kg（Qdrant 挂 = 语义检索空转）。

**速记规则**（供注入模板/SOUL.md 使用）：
1. T1-T4（事实/变更/历史/排障）→ **默认搜**，命中率信号只降级不取消。
2. T5-T7（代码/探索/机械）→ **默认浅搜或不搜**，仅出现明确引用（服务名/配置名/路径）时升级为搜。
3. 宽泛词不查（"系统/服务"→噪音）；同任务 L1 自动查询 ≤1 次。

## 4. 降级成本：不搜乱查的代价 vs 搜了无用的代价

| 维度 | 假阴性：不搜 → terminal 乱查 | 假阳性：搜了但无用 |
|---|---|---|
| 直接成本 | 8-40K effective（grep/find/curl 2-4 次，同样被重放放大） | ~5K effective（裁剪后）；25K（未裁剪） |
| 命中率 | 字符串匹配，猜词失败率高 | 语义检索，命中率更高 |
| 错误风险 | **高**：猜错 → 输出错 → rework 5-20K + 用户纠正 | 低：无错误输出，纯浪费 |
| 违背用户原则 | **是**（明示禁止）→ 可能被中断 | 否 |
| 可检测性 | 无界（可能无限乱查下去） | 有界（一次 2.5K，冷却 30s 不重试） |
| 附加损失 | 结论不自动入库 → 未来任务重复踩坑 | 跨项目噪音可能误导（实测：查 user-center 命中 doctor-center Config） |

**不对称比：假阴性 ≈ 2-5× 假阳性（纯 token），计入用户介入与决策污染后 ≈ 10-20×。**

> **结论 3：决策偏置原则——T1-T4 宁可假阳性（多搜一次浪费 5K），不可假阴性（漏搜出错 20K+ 且违背原则）；T5-T7 反之，用明确引用信号升级。** 搜索是"可检测的有界浪费"，乱查是"不可控的无界错误"。

## 5. 缓存 TTL 经济性

**经济模型**：缓存命中省一次 search 的 effective 成本（裁剪后 ~5K）。失效代价 = 旧数据风险（只对 T1/T2 关键事实有意义）。KG 是**写少读多**（build/memorize 分钟-小时级低频，查询高频）→ 缓存方向正确。

**TTL 的真实经济价值 = 防碎查，不是防正常查询**：agent 同任务重复查同 query（碎查）才是主要浪费源；正常的一次性查询本来就要付。因此**节流规则（同 session 同键 1 次/分钟）是主防线，TTL 是次防线**。

| 项 | 原设计 | 建议 | 理由 |
|---|---|---|---|
| sense TTL | 120s | **300s** | 任务内多次 LLM 调用共享；典型任务 <5 min；跨任务新 sense 是强制层反正重查 |
| search TTL | 60s | **300s** | 防同任务碎查；静态事实（基础设施/配置）变化周期小时-天级，300s 远小于变化周期 |
| 写后失效 | 立即 | **保持（硬失效 > TTL）** | 动态索引（methods/classes）随 build 变，TTL 管不住，必须写失效兜底 |
| L2 Cypher | 不缓存 | 保持 | 精确查询每次要新鲜属性 |
| 跨会话 | 不缓存 | 保持 | 环境可能已变，新会话 fresh sense 是强制层 |

**失效优先级：写操作硬失效 > 用户"重新看"强制失效 > TTL 软失效。**

## 6. 预算上限规则（单任务）

**raw 预算：单任务 KG 搜索注入总量 ≤3K tokens**（沿用三层分配，本模型给出超限处置）：

| 层 | raw 预算 | 实际形态 |
|---|---|---|
| L0 sense 简报 | ≤800 | 状态行 50-100；简报 300-500，每会话一次 |
| L1 search_kg | ≤2K | limit=5；注入时裁剪转述 top-3 ≤500（**执行点**） |
| L2 Cypher | ≤700 | 字段白名单，只取所需属性 |

**effective 预算：≤15K tokens（3K raw × m=5 保守放大）——通过"注入永远是裁剪摘要、绝不注入原始输出"实现。**

**超限处置阶梯**：
1. 第 1 次 search_kg 结果 > 2.5K raw → 强制裁剪 top-3 + 字段白名单（title/entity_type/snippet/hop/关键属性），丢弃 score 浮点/score_breakdown/llm_analysis/evidence 大段原文。
2. 同任务第 2 次 L1 → 降级为定向 L2（白名单更小）或直接用简报覆盖；需明示理由。
3. 第 3 次 → **禁止自动查询**，标记 `⚠ KG 查询超预算`，改磁盘直查，明示用户。
4. 空结果/全低分 → 正常语义（KG 确实无数据），冷却 30s 不重试，降磁盘。
5. 超时 >10s → 视为降级，不等 MCP 的 120s 兜底。

**绝对禁止**：
- `dt search limit=10` 结果注入（4-5K raw = 40-50K effective）。
- 每轮 pre_llm_call 裸查（注入的不是完整 JSON，而是缓存简报压缩的 1-2 行状态摘要）。
- 碎查（同任务 >1 次 L1 自动查询需理由）；宽泛词查询。

## 7. 落地要点（与集成方案对齐）

1. 本模型的**执行载体 = 注入模板中的"搜索触发"行 + SOUL.md 决策清单**（见 `2026-08-11-pre-llm-call-injection-final.md`）——矩阵压缩为速记规则 3 条，完整矩阵本文件为准。
2. **预算会计**：插件/agent 每任务累计查询次数与 raw 大小，超限走第 6 节阶梯。
3. 决策偏置是**软规则（agent 语义判断）**，唯一硬强制是 L0 简报注入；矩阵用于把"凭感觉决定搜不搜"变成"按任务类型×命中率×新鲜度决定"。
4. 与降级策略衔接：KG 故障时矩阵整体退化为"浅搜 + 磁盘直查"，绝不阻塞主流程（KG 是加速器不是单点依赖）。
