# dt router 无检索锚点查询拦截 —— 排查与方案评估总结

> 日期：2026-09-04
> 范围：`dt router` 智能路由搜索命令（digital-twin-v2 Rust 项目）
> 关联代码：`src/interfaces/cli/router.rs`、`src/application/context/fusion.rs`、`src/application/context/search_mcp.rs`、`plugins/dt-router/__init__.py`
> 本文档记录"是否应该搜索知识图谱"这一判定的完整排查过程与所有被实测证伪的替代方案，供后续评估其他解决方案时参考。

---

## 1. 问题现象（用户原始反馈）

1. **简单的闲聊拦截无法完全阻止无必要查询**：`帮我实现`、`给我一些建议`、`分析某个文件的内容`、`帮我检查确定的原因，分析当前项目下的代码` 这类没有具体可检索对象的查询，仍然触发了 KG 搜索。
2. **LLM 结果过滤不起作用**：过滤后结果几乎没减少，无效内容没被滤掉。
3. **Hermes 下默认每次查询都是全局的**（world=all），查询 code / 知识 / 记忆没有区分。

---

## 2. 根因分析（实测确认）

### 2.1 L0 闲聊拦截为什么漏

- L0 是闲聊词表（`casual-words.txt`）分词器，只拦寒暄（"你好/在吗"等）。
- "帮我实现/给我一些建议/分析某文件"不是闲聊，是**任务句**；只要混入词表外的字词就放行。
- 本质：闲聊分类器 ≠ 任务/无锚点拦截器。

### 2.2 LLM 结果过滤为什么没起作用

两个独立 bug 叠加：

1. **`judge_relevance` 解析顺序错误**（原有 bug，非本次引入）：
   - 原逻辑先查 `norm.contains("相关") && norm.contains("不相关")`；
   - 因字符串"不相关"**包含子串"相关"**，对纯"不相关"响应恒为 true → 走"保守保留"分支，返回 `Ok(true)`；
   - 结果：LLM 即使返回"不相关"，命中也被保留，过滤形同虚设。
   - 修复：改为先 `starts_with("不相关")` → 移除；再处理混合词；再 `contains("不相关")`；最后才 `contains("相关")`。

2. **LLM 过滤上下文过窄**：
   - 只喂 title + snippet（行号），signature / llm_analysis / project / relations / content 均未传入；
   - 修复：升级为完整 SearchHit 上下文（signature / llm_analysis / project / relations / file_type / entity_type / source_world 等）。

### 2.3 Hermes 下每次 world=all 的链路

- 调用端 `plugins/dt-router/__init__.py` 的 `_run_router` **不传 `--world`**；
- CLI（`main.rs` 的 Router 命令）默认 `world=all`；
- 但插件已从 cwd/消息解析出 project 并传 `--project`，实际是当前项目聚类而非全库检索。
- 建议：路由职责放调用端、world 显式传入（插件按消息内容判断），而非用自然语言猜世界。

## 3. 当前实现（可工作，已落地）

### 3.1 L0 规则强信号拦截（可靠、零成本、默认生效）

`should_search` 升级为两道闸：

1. **闲聊词表完整切分** → 拦；
2. **`has_search_anchor()` 锚点检测** → 无检索锚点即拦。

锚点定义（`has_search_anchor`）：

- 代码语法：`::` / `()` / `fn` / `def` / `class` 等；
- 文件后缀 / 路径：`.rs` / `.php` / `config/` 等；
- 驼峰 / 蛇形标识符：`MemgraphClient`、`getBalance` 等；
- jieba 去虚词后的非通用内容词。

中文兜底用 `GENERIC_ANCHORLESS_WORDS` 词表（内置默认），**已外置为 `config/anchorless-words.txt`**：

- 外部文件与内置默认**并集叠加**（只增不减，不会因只写几词丢失默认覆盖）；
- 查找顺序：环境变量 `DT_ANCHORLESS_WORDS_FILE` → `<CWD>/config/anchorless-words.txt` → `~/.config/digital-twin/anchorless-words.txt` → 可执行文件目录；
- 日常遇到漏网句式，只需往该文件加词，**无需改 Rust**；
- 验证：外部加"整理"→"帮我整理一下"被拦；去掉→回内置放行。

### 3.2 LLM 结果过滤（保守版，受 `kg_router.result_filter.enabled` 开关控制，默认关）

- 修复了"不相关"子串解析 bug；
- 上下文升级为完整 SearchHit；
- 提示词改为**保守双门槛**：只删"明确不相关"的命中，不做一刀切无锚点判定（因 Hunyuan-MT-7B 判别力不足，激进版会把有锚点查询如 Wxapp/支付超时也误删）；
- 默认行为不变：`dt search` 不受影响。

### 3.3 测试状态

- `cargo test --lib`：**693 passed; 0 failed; 1 ignored**（含新增用例 `anchorless_task_chatter_is_blocked_at_l0`：5 拦 + 6 放行）。
- 端到端验证：

| 帮我实现 / 给我一些建议 / 分析某个文件的内容 / 介绍一下有哪些模块 / 有什么问题 / 帮我检查确定的原因，分析当前项目下的代码 / 帮我检查一下原因 / 看下现在项目代码的问题在哪 | world=none，拦截 |

## 4. 被实测证伪的替代方案（重要）

> 以下方案均已用真实模型/真实查询实测，结论是"不可行"或"不提供超过现状的判别力"。引用这些结论时请带原始数据。

### 4.1 向量相似度（embedding 判"有无锚点"）—— 不可行

**假设**：embed 查询与"无锚原型"相似度高 → 无锚拦截；与"实体种子"相似度高 → 有锚放行。

**实测 1（整句级）**：
- 无锚句 A"帮我检查确定的原因，分析当前项目下的代码" 与 有锚句 B"帮我检查支付超时的原因" 相似度 **0.695**；
- A 与同类无锚句 C"帮我检查一下原因" 相似度反而只有 **0.633**；
- 同句子模板换不换实体词，embed 几乎不敏感，阈值无法分开。

**实测 2（逐词级：jieba 词 vs 实体种子相似度）**：
- 抽象词"确定/当前/项目/分析/实现/检查/看"与实体种子（问题/异常/服务/配置/对账）相似度全在 **0.6~0.68** 区间；
- 与真实体词（支付/订单/超时）自相似 1.0、异词 0.7+ 的分布严重重叠；
- 设任何阈值都会把"原因/问题"当实体放行，或把"支付"当抽象误拦。

**根因**："有无检索锚点"是**结构属性**（句子里有没有可索引的命名实体/文件名/符号），不是**语义相似度属性**。通用 embedding（bge-m3）把高频抽象词嵌在语义中心区，学不出这种逻辑差别。

### 4.2 LLM 替代 NER（判"有无锚点"）—— 当前可用模型全部不行

**实测（3 个模型，同提示词，temperature=0）**：

| 模型 | 无锚组命中 | 有锚组命中 | 合计 |
|---|---|---|---|
| tencent/Hunyuan-MT-7B（当前配置） | 5/8 | 4/8 | **9/16 ≈ 56%** |
| deepseek-ai/DeepSeek-R1-0528-Qwen3-8B | 2/3 | 1/4 | **3/7** |
| deepseek-ai/DeepSeek-V3.2 | — | — | 503 服务不可用 |

**典型错误**：
- 有锚误判无："MemgraphClient::new"→没有、"帮我实现一个轮询功能"→没有、"为什么订单重复扣款"→没有、"redis 缓存穿透怎么解决"→没有（R1-8B）；
- 无锚误判有："给我一些建议"→有、"帮我检查确定的原因，分析当前项目下的代码"→有（Hunyuan）；
- "有什么问题"→跑题输出一大段解释（Hunyuan）。

**结论**：不是提示词问题。8B 级模型对"轮询/扣款/缓存穿透/回调是业务实体"需要领域常识 + 代码符号理解，做不好。且每查询多一次 LLM 调用（延迟 + token 成本 + 单点故障），放 Hermes pre_llm_call 热路径不划算。即便判断准了，与现有词表差集法（这批难例 100% 正确）相比也是倒退。

### 4.3 jieba posseg 词性（方案 4）—— 不可行

**假设**：业务实体词（支付/轮询/扣款）与抽象词（原因/问题/建议）词性不同，可按词性分离。

**实测**：

| 词 | 词性 | 类别 |
|---|---|---|
| 原因 / 问题 / 建议 / 模块 / 代码 / 项目 / 功能 | n / vn | 抽象词 |
| 订单 / 扣款 / 回调 | n / v | 业务实体 |
| 支付 / 配置 / 缓存 | v | 业务实体 |
| 超时 | **b（区别词）** | 业务实体 |
| redis / payment / MemgraphClient / Wxapp / help / new | eng | 代码符号 |

- **词性重叠**：抽象词（原因=n、问题=n、建议=n、模块=n）与业务实体（订单=n）同为 n，无法靠词性区分；
- **反向误杀**：中文真实实体常标成 v/b（支付=v、超时=b、扣款=v），若按"取名词性词为实体"会把核心实体过滤掉；
- **唯一新信号**是 eng（英文/代码符号），但已被规则强信号（标识符/文件名/路径）覆盖。

**结论**：posseg 不提供超过现状的判别力。方案 4 不成立。

## 5. 核心认知

"有没有可检索锚点"是**结构/逻辑属性**：

| 技术 | 为何不行 |
|---|---|
| embedding（bge-m3） | 语义相似度 ≠ 结构属性；同模板换实体词 embed 不敏感 |
| 弱 LLM（≤8B） | 缺领域常识与代码符号理解，判断接近抛硬币 |
| 词性（posseg） | 中文业务实体词性分布（v/b/n）与抽象词重叠，区分不开 |

目前最准的实现是**规则 + 词表差集**：这批难例 100% 正确、零延迟、零成本、可解释。局限是词表需人工维护（已外置 `config/anchorless-words.txt`，日常加词无需改码）。

**评估任何新方案的判断标准**：
1. 能否理解"业务实体 vs 抽象词"的语义边界（弱模型做不到）；
2. 是否有结构信号（embedding 没有）；
3. 维护成本能否接受（词表要人管）。

## 6. 已知遗留项（未处理）

- **RRF 融合分数恒值问题**：`fusion.rs` 的 `rrf_hits` 用 `1/(60+rank)`，top-1 ≈ 0.0164，把 code/knowledge/doc 精确通道（0.9~0.95）与向量通道（>0.3）压成等值，与真实相关度断钩。改动会波及 `dt search` 行为，需用户确认后再动。
- **world 区分**（用户反馈第二点）：路由职责建议放调用端（`plugins/dt-router`），world 显式传入，而非 CLI 默认 all + 自然语言猜世界。
- **词表维护**：新句式可能漏，靠人工往 `config/anchorless-words.txt` 加词。
