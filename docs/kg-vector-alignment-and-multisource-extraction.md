# 知识图谱 × 向量库对齐 + 多源 LLM 标准抽取

> 日期：2026-09-05
> 状态：方案设计
> 原则：
> - **知识真相只有两份**：Memgraph（图谱）+ Qdrant（向量投影）
> - **SQLite 仅作增量状态记录器**：文件变更检测 / LLM 抽取去重，不参与知识真相、不做检索
> - 参考《知识图谱+向量融合方案.md》的"图谱/向量各司其职、互为补充、可降级"哲学
> - 尽量简化：多源冲突用单节点多源属性解决，不做版本化子图
> - **实现载体：全部用 Rust**（scripts/opencode-after-edit.sh、batch-llm-extract.py 等脚本仅作行为参考/原型验证，不进入正式实现）

## 1. 构建工作流（详细）

> 打个比方：构建就像"图书馆进新书"。书（源文件）进馆后，要经过拆章、请专家写内容简介、把卡片分放两个柜子、登记台账这几步，之后读者（检索）才能查到它。
> 对应代码位置：`src/application/build/service.rs`、`src/application/build/pipeline.rs`、`src/application/pipeline/processors/`、`src/application/sync/kg_bridge.rs`。

### 1.1 一句话流程

```
源代码 / 文档 / 配置文件（都是 root 下的普通文件）
        │
        ▼ 第 1 步：看文件变没变（算指纹）
        │
        ▼ 第 2 步：变了的文件，拆解出"内容块"
        │
        ▼ 第 3 步：请 LLM 读懂每个块，抽出：
        │         · 提到了谁（实体）
        │         · 谁和谁什么关系（关系）
        │         · 每段内容讲什么（描述/摘要）
        │
        ▼ 第 4 步：写进两个"柜子" + 记台账
        │
        ┌──────────────────────────────────────┐
        │  柜子 A：图谱库（存"谁和谁有关"）      │
        │  柜子 B：向量库（存"每块内容的语义"）   │
        │  台账：SQLite（存"哪个文件处理过"）    │
        └──────────────────────────────────────┘
```

### 1.2 什么时候触发构建

| 场景 | 怎么触发 | 干什么 |
|------|---------|--------|
| 手动全量或增量 | `dt build` / `dt build --full` | 扫描配置好的 root，处理新文件或改动过的文件（配置文件也在内，当普通文件处理） |
| 只改了单个文件 | `dt build --file <路径>` | 只重处理这一个文件，秒级完成，适合编辑器里改完即刷新 |
| 定时巡检 | cron 定期 reconcile | 对比两个柜子的数量，把漏掉的补上（见第 7 章） |

### 1.3 每步具体做什么

**第 1 步：判断哪些文件要处理（增量检测）**
- 给每个文件算一个"指纹"（文件内容的校验值 + 修改时间）
- 拿指纹跟台账（SQLite）里记的比对：一样 → 跳过（没改过）；不一样或是新文件 → 进入处理
- 这样第二次构建只处理改动的文件，不用全部重来

**第 2 步：把文件拆成内容块**
- 代码文件：按编程语言的语法结构拆——一个方法一块、一个类一块（用 tree-sitter 语法解析器）
- 文档/文本：按长度切块，超过 8K 字符就切开，每块带着标题前缀，保证小块自己能读懂上下文

**第 3 步：LLM 读懂内容，抽实体、关系、描述（最耗时的一步）**
- 把每个内容块发给大模型，用 JSON 格式返回三类信息：
  - 实体：这段讲了哪些事物（如"Hermes Agent""Hooks 钩子"），带类型（服务/工具/概念…）、别名、一句话描述
  - 关系：谁和谁是什么关系（如"Hermes Agent 使用了 Hooks"）
  - 描述：这段内容的核心摘要
- 实测数据：一篇中型文档约 2-3 分钟；整个 hermes-docs-zh 39 篇抽出 936 个实体、612 条关系
- 速度瓶颈在这：模型一次要 1-3 分钟，全量代码（如 .hermes 15.9 万个方法）全部走 LLM 不现实，这也是方案里要先对齐、按需抽取的原因

**第 4 步：写进两个柜子 + 台账**
- 柜子 A（图谱库）：把实体建成节点，关系建成连线。**同一个实体反复出现不会重复建**，而是合并进已有节点（按 root+类型+规范名 找，找到就更新、没找到才新建）
- 柜子 B（向量库）：给每个实体的描述/内容块算一个"语义向量"（一串数字，代表意思），存进向量库，供以后按意思检索
- 台账（SQLite）：记下"这个文件已处理、指纹是多少"
- 三个地方都写成功了才算完成。写到一半失败也不要紧：下次构建发现台账没更新会重试，天然安全

### 1.4 删除文件怎么处理

删的顺序有讲究：先从向量柜删掉它的语义数据 → 再从图谱删节点和连线 → 最后更台账。防止删到一半检索出"幽灵"。

### 1.5 这套流程将来要补的缺口

- 文档的实体抽取目前只有原型验证（Python），要并入 `dt build` 同一管线（文档和代码、配置一样处理，仅 doc_type 标签不同）
- 单个文件更新（`dt build --file`）现在只做了解析、还没写进柜子，需要补全第 4 步
- 配置文件（Nacos 下载到本地的）以后走完全相同的流程，只是标签记为"配置"

## 2. 搜索工作流（详细）

> 打个比方：搜索就像"去图书馆找书"。读者（你）报出需求，图书管理员会走几条路找：先查书名册、再按内容相似度翻卡片柜、翻不到就按关键词挨个书架找，最后把找到的书连同"相关推荐"一起给你。
> 对应代码位置：`src/application/context/search_mcp.rs`（代码/文档/配置搜索）、`src/application/knowledge/extract/retrieve.rs`（知识图谱搜索）。

### 2.1 先决定搜哪个"世界"

用户发出检索请求时，先看他想搜哪类内容（world 参数），决定去哪个柜子找：

| 想搜什么 | 去哪个柜子找 |
|---------|-------------|
| 代码（方法/类） | 代码向量柜（code_methods + code_classes） |
| 文档 | 文档向量柜（doc_chunks） |
| 配置 | 配置柜（config_chunks + doc_chunks） |
| 知识/记忆/实体 | 图谱柜 + 图结构本身（kg_nodes + 顺着连线走） |
| 不指定（all） | 上面全找一遍再合并 |

### 2.2 搜代码：三条路同时找，结果合并

用户问"有没有个方法叫 xxx"或"哪个函数做了 yyy"时，程序走三条路：

```
你的问题
  │
  ├─ 路 1：精确点名（名字完全对上）
  │     在卡片里精确找"名字 = 你的输入"，找到就高分置顶
  │     ——适合你记得准确名字时
  │
  ├─ 路 2：按意思找（语义搜索）
  │     先把你的问题变成"意思向量"，去向量柜里找意思最接近的
  │     再把候选里前 50 个用更精细的向量再排一次，保证排前面的真相关
  │     ——适合你不记得名字、只记得大概功能时
  │
  └─ 路 3：关键词兜底（结果太少时才走）
        直接翻卡片，找名字里含你关键词的，给个保底低分
        ——防止上面两条路都落空时无结果

三条路的命中合在一起，按分数从高到低，取前 N 个给你。
最后一步：对结果里的"代码"，去图谱库查一下它调用了谁/被谁调用，把邻居关系也附上。
```

分数设定：精确点名最可信（0.95 近乎满分），意思相近其次，关键词兜底最低（0.28 保证可达）。低于 0.3 分的噪声直接丢弃。

### 2.3 搜文档/配置

- 文档：跟代码类似，把问题变向量，去文档柜里找意思接近的内容块，再按来源文件过滤
- 配置：配置已下载到本地当普通文件，走和文档一样的路，只是标签是"配置"。找"数据库连接串在哪个配置里"这类问题时能直接定位到具体配置文件的某一段

### 2.4 搜知识/记忆：先找线索，再顺着图走（最体现"图谱"价值）

这是和普通搜索最大的不同——不只返回"找到的东西"，还**顺着关系网往外走几步**，带回相关的一圈。分五步：

```
第 1 步：先找几个"线索点"
        · 按意思找：问题变向量，在向量柜找最接近的知识点
        · 按名字找：名字和你的关键词能对上的（如 "redis"）强制进来
          ——防止专有名词因为意思向量不够像而被漏掉

第 2 步：顺着图往外走（图谱的独有价值）
        找到线索点后，去图谱里看它连着谁：
        · 它有别名？把别名节点也带上（A 也叫 B，B 也相关）
        · 它通过关系连着谁？往外走 1-2 步，把邻居都带上
        比如搜"Hermes Agent"，会带回"它使用 Hooks、它依赖配置、它管理会话…"
        ——这一步是普通向量搜索做不到的

第 3 步：合并去重，控制数量
        把线索点和走图带回来的邻居合成候选池，去掉重复，按相关度分桶截断

第 4 步：精排（可选）
        如果配置了重排模型，把候选再精排一次；没有就跳过

第 5 步：算总分，返回
        综合"线索点的相似度 + 离线索点的远近"打分：
        越近的分越高（直接命中 > 隔一层 > 隔两层），取前 N 个返回
```

**出问题时的"降级"**（保证不崩）：
- 向量柜挂了 → 明确告诉你"语义搜索不可用"，返回空
- 图走不动 → 退回只用向量柜的结果，不算错
- 精排没配 → 直接用基础分

### 2.5 现状 vs 目标（这套流程要补什么）

| 现在的短板 | 为什么 | 方案目标 |
|-----------|--------|---------|
| 文档里抽出的实体没进图谱 | 文档目前只存了"整块内容"的向量，没存"里面提到谁" | 文档实体抽取后进图谱，搜实体时能顺着文档关系网走 |
| 不同来源的同名实体没打通 | 代码里的"Gateway"和文档里的"Gateway"互不相识 | 统一 schema 后，用"指的是同一个"关系连起来，搜一个能带出另一个 |
| 同一事物两种矛盾描述时没提示 | 实体没进图谱，冲突无从谈起 | 有冲突的实体检索时把多个版本描述一起给你 |
| .hermes 内容搜不到 | 它只有图、没向量 | 补向量后即可搜到 |

### 2.6 实战案例：搜"订单号生成规则"——向量与图怎么配合（实测）

> 本节用真实数据和真实搜索结果，说明"换着说法问同一个问题"时，向量库与图关系库各自做什么、为什么必须配合。

**先看现状图的缺陷（实测）**：图里同时存在"支付订单号"（type=Config，aliases:[payOrderId]）和"支付系统订单号"（type=Standard）两个节点——只差"系统"二字却互不相识（无 SAME_AS），且都没连到真正生成订单号的方法 `SeqKit.genPayOrderId`（注释即"生成支付订单号"）。文档实体 ↔ 代码方法是断的。

**但搜代码时，向量库一次就答全了**。真实搜索（world=code, project=offen-pay）：

| 问法 | 向量召回第 1 名 | 得分 |
|------|----------------|------|
| "生成支付订单号" | genPayOrderId (SeqKit) | 0.79 |
| "支付订单号生成规则" | genPayOrderId (SeqKit) | 0.75 |

命中的方法自带 `llm_analysis` 摘要，直接给出完整答案：
> "用途：生成支付订单号。逻辑：根据是否使用 MP_ID 来决定订单号的前缀：使用则用前缀+IdWorker 生成 ID；否则用固定格式的日期+时间+顺序号。"

**为什么向量能答、图靠实体名匹配答不了？**

| | 图（靠实体名匹配） | 向量（靠语义） |
|--|------------------|---------------|
| 搜"支付订单号生成规则" | 图上实体叫"支付系统订单号"，名字对不齐，且没连生成方法 → 找不到 | 方法 llm_analysis 里就有"生成支付订单号 + 规则描述"，语义完全匹配 → 找到 |
| 换一百种说法 | 每种都得靠实体名/别名穷举 | 说法意思接近就能命中，无需穷举 |

**关键洞察**：**代码方法节点自带 LLM 摘要（用途+逻辑），是回答"怎么做/规则是什么"的最佳载体**——比文档里抽出的概念实体更适合。搜索"XX 怎么生成/规则"，直接搜方法（world=code）往往一次命中。

**那图关系库的价值在哪？——补全"调用链/上下文"，向量给不了**。同一命中返回里带 relations：
- genPayOrderId `called_by` createOrder（下单入口调它）
- genPayOrderId `called_by` executeOrder / genPayOrder（订单流程调它）
- genPayOrderId `belongs_to` SeqKit（工具类）

向量说"有这么个生成规则"，图说"它在 createOrder/executeOrder 流程里被调用"——一个是内容，一个是结构。

**两库配合的正确搜索流程**：

```
用户问"支付订单号生成规则"
   │
   ▼ ① 向量库语义召回（主力，解决"换说法"）
        → 命中 genPayOrderId，llm_analysis 给出完整规则
        → 顺带带回 called_by 关系（createOrder/executeOrder/genPayOrder）
   │
   ▼ ② 图关系库扩展（补充链路）
        → 从 genPayOrderId 沿 CALLS 走，得到调用链
        → createOrder → genPayOrderId → format/getAndIncrement/getIdStr
   │
   ▼ ③ 合并返回
        内容（生成规则文字）+ 结构（谁调用它、在哪个流程）
```

**结论**：向量负责"找到对的点"（换说法也能命中），图负责"把点的关系圈带全"。二者不是二选一，是配合。

**当前缺口**（正是方案要补的）：若不带 project/code 过滤、在知识世界搜"订单号"，向量只能召回文档实体"支付系统订单号"（描述"支付系统生成的唯一订单号"），不会自动带上代码方法 genPayOrderId 的生成规则——**跨世界（文档实体 ↔ 代码方法）没有桥**。补桥（SAME_AS/GENERATES，见第 6 章）后，world=all 时向量召回实体 → 图沿桥走到方法 → 带出方法的摘要，才是完整答案。

## 3. 角色定位（谁管什么）

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  Memgraph    │   │  Qdrant      │   │  SQLite      │
│  知识真相     │   │  检索投影     │   │  增量状态     │
│              │   │              │   │              │
│ 实体/关系/    │   │ 节点语义向量  │   │ 文件 sha1+mtime│
│ 多源属性/冲突 │   │ business_id  │   │ LLM 去重进度   │
│              │   │ 1:1 映射     │   │              │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │ 写真相           │ 可随时从图重建    │ 只记录"已处理到哪"
       └──────────────────┴──────────────────┘
```

- **Memgraph = 真相**：实体（含 type/summary/aliases/summaries[]/source 属性）+ 关系（含 confidence/evidence）
- **Qdrant = 投影**：为检索而生，business_id ↔ 图节点 1:1（sha256，kg_bridge.rs 已有）；**丢失可从图重建**
- **SQLite = 增量账本**：只回答"源文件变没变、这篇文档抽没抽过"，**不回答任何知识问题**；丢了重建成本低（重新扫描对比源文件）

**设计精神**：图谱与向量各司其职、互为补充，任何一路失败不影响整体（向量挂了图仍可用，图挂了向量仍可召回）；多源描述不丢、检索时同返；每步有降级路径。

### 3.1 命名澄清：project 实为"索引根路径的别名"，建议正名 root

现有代码/数据里的 `project` 字段，语义**不是"软件项目"**，而是**被索引根路径的短别名**。实证：

- config.yaml 项目定义为 `base + item`（item 可带别名）：`{"message-center": "uv-message-center"}`、`{"boss": "boss/boss"}` —— 名字是给人看的标签，与目录名无关
- Memgraph 里 project 五花八门：`.hermes`、`软件`、`nacosConfig`、`luis-env`、`charts-prod` —— 这些是文档目录/配置根/记忆根，不是项目
- 同一物理路径可对应多个 project（`offen-pay` 在 `/others` 与 `/others/pay` 各索引一次）—— project 不唯一对应 path
- 检索过滤、dt:// id、向量 payload 全用 project 作**命名空间隔离键**

准确模型是三层：

| 概念 | 建议命名 | 例子 | 本质 |
|------|---------|------|------|
| 索引根绝对路径 | `root` | `/data/myProject/digital-twin-v2` | 被扫描的起点 |
| 根的短别名（现 project） | `root_id`（代码兼容期仍叫 project） | `digital-twin-v2`、`软件` | 过滤/id/显示的稳定键 |
| 文件相对路径 | `rel_path` | `src/main.rs` | 文件在 root 下的位置 |

要点：
- **不能只记 path**：绝对路径有机器差异且太长，别名是稳定检索键
- **不该叫 project**：多数"项目"实为文档/配置/记忆根，叫 project 语义污染（会让人误以为一个 project=一个 git 仓库）
- **本方案统一用 root 语义**；代码字段 project 因穿透面大（Memgraph 属性/Qdrant payload/dt:// uri/SQLite 主键/CLI/MCP）**本轮不改名**，只在新 schema 与文档中澄清，避免语义继续污染
- 一个 root 可含多种 source_type（如 digital-twin-v2 root 下同时有代码、docs 文档、skills 记忆）—— source_type 与 root 是正交的两个维度

## 4. 对齐方案（存量修复）

### 4.1 对账（图 vs 向量，SQLite 辅助归因）

```
图侧计数:  MATCH (n) RETURN project, labels(n)[0], count(*)
向量侧计数: Qdrant 每 collection 按 project count
SQLite:   file_snapshots 提供"哪些文件已建图"→ 辅助判断缺向量的根因
对账输出:  有图无向量清单 / 有向量无图孤儿清单
```

### 4.2 修复动作

| 场景 | 动作 | 成本 |
|------|------|------|
| .hermes 15.9 万方法有图无向量 | kg_bridge 批量补 embed（图里已有 AST 摘要，不重跑 LLM） | ~27 min |
| Entity 26k 仅 8,950 进向量 | 对账后把**有 summary 的 Entity** 补 bridge 进 kg_nodes | 中 |
| 孤儿 point（有向量无图） | 按 business_id 反查图，查不到即删 | 低 |

**对齐量化标准**：每 (project, 类型) 桶 `|图-向量| / 图 < 1%`，孤儿 = 0。

## 5. 多源 LLM 标准抽取

### 5.1 数据源与统一 schema

| 源 | 抽取方式 | 现在 |
|----|---------|------|
| 代码 | tree-sitter + LLM 摘要 | 已有 |
| root 文档 (hermes-docs-zh 39 篇) | **LLM JSON mode 抽取**（Rust 实现，原型 batch-llm-extract.py 已验证 936 实体/612 关系） | 需移植为 Rust |
| 本地配置（下载到 root 下，普通文件） | 启发式规则 + 可选 LLM（同文件管线，label=config） | 需接入 |
| 记忆/技能 | dt memorize | 已有 |

**统一 schema**（实体/关系/描述，已实测通过）：

```json
{
  "root_id": "digital-twin-v2",        // 索引根别名（代码字段兼容期仍叫 project）
  "source_type": "doc",                // code|doc|config|memory
  "doc_id": "dt://doc/digital-twin-v2/user-guide/features/hooks.md",
  "entities": [{"name":"Hooks","type":"Concept","aliases":[],"summary":"...","confidence":0.95}],
  "relations": [{"head":"Hermes Agent","tail":"Hooks","type":"USES","confidence":0.9,"evidence":"原文"}]
}
```
类型白名单：Service/Module/Tool/File/Technology/Concept/Platform
关系白名单：CONTAINS/DEPENDS_ON/USES/IMPLEMENTS/CALLS/MANAGES

### 5.2 抽取→入库

```
LLM 抽取(4并发, JSON mode, 分块8K)
  → 归一化(aliases字符串→list, summary补空, 过滤非dict)
  → MERGE 进 Memgraph(实体带 source/doc_id 溯源)
  → bridge 同步向量(kg_nodes)
```

幂等：实体按 `(project, type, canonical_name)` MERGE，重跑不重复。
**去重靠 SQLite build_progress**：文档按 file_sha1 记"已抽取"，内容没变不重抽。

### 5.3 代码方法与概念实体建桥（回答"XX 怎么生成/规则"的关键）

实测教训：搜"订单号生成规则"这类**问做法/规则**的问题，向量库直接命中代码方法 `genPayOrderId`（其 LLM 摘要含"用途+逻辑"）——**方法比文档抽出的概念实体更适合回答"怎么做"**。但文档实体（"支付系统订单号"）与代码方法（genPayOrderId）之间目前无桥，跨世界（doc→code）搜不到完整答案。

建桥规则（构建时 LLM 完成）：
```
文档抽出概念实体 E（如"支付系统订单号"，描述"支付系统生成的唯一订单号"）
代码侧方法 M 的摘要/注释与 E 语义吻合（如 genPayOrderId 注释"生成支付订单号"）
→ 建桥: MERGE (M)-[:GENERATES]->(E)    // 方法产出该实体
  或    MERGE (M)-[:IMPLEMENTED_BY]->(E) // 概念由该方法实现
```

效果：world=all 搜索时，向量召回文档实体 → 图沿 GENERATES 走到方法 → 带出方法摘要（规则/逻辑），跨源答案完整。此桥也是 §6 消歧的基础。

## 6. 冲突清洗（多源描述不同/互斥）

**简化哲学：单节点多源属性，不做版本化子图。**

### 6.1 单节点多源属性

```cypher
(:Entity {
  name: "Hermes Agent",            // 规范名
  type: "Service",                 // 规范类型
  aliases: ["AIAgent", "Agent"],
  summary: "融合后的当前描述",       // 检索默认用这条
  summaries: [                     // 各源原文描述（保留不删）
    {text: "智能代理", source: "docs/hooks.md", confidence: 0.95, ts: "..."},
    {text: "AI 聊天助手", source: "memory/xxx", confidence: 0.7, ts: "..."}
  ],
  conflict_status: "resolved|unresolved",  // 有互斥才置 unresolved
  provenance: ["docs/hooks.md", "skills/SKILL.md"]
})
```

### 6.2 清洗流程（3 步：规则优先、LLM 兜底）

**① 规范化（确定性规则，消灭伪冲突）**
- name 大小写/空白归一，中英别名进 aliases（CLI vs cli 不打架）
- 类型同义词映射（Chatbot→Service）

**② 合并/消歧**
- 同名不同 source → MERGE 成一个，描述并入 summaries[]
- 异名同指 → `SAME_AS` 关系（检索图查询扩一跳展开），不物理合并
- 同名异指（不同项目 Gateway）→ 靠 project/domain 区分，不合并

**③ 冲突消解（描述不一致/互斥）**
- 不同源描述不同：多数派/高置信度/新 → 置为当前 `summary`，其余留 summaries[]（**永不丢原文**）
- **互斥无法自动判**：`conflict_status: "unresolved"`；检索到该实体时多版本描述一并返回（融合方案"多路召回"精神），由人判断
- 可选：LLM 仲裁——互斥双方+来源喂 LLM 出融合描述，人工确认写回

### 6.3 关系清洗

- 去重：(head, tail, type) 三元组，evidence 拼接
- 白名单外类型（实测 0.65%）→ 映射归一或删
- 方向规范：DEPENDS_ON 统一 A→B

## 7. 增量维护

**SQLite 的 file_snapshots / build_progress 保留，负责"什么变了"；图/向量负责"有什么知识"。**

| 需求 | 存储 | 机制 |
|------|------|------|
| 文件变更检测 | SQLite file_snapshots | 扫描时算源文件 sha1+mtime，与表中比对；变了的文件重走 build（tree-sitter→LLM→store） |
| LLM 抽取去重 | SQLite build_progress | 文档按 (file, sha1, stage) 记已抽取；内容没变不重抽（已有实现，实测有效） |
| 文档知识抽取增量 | 同上 | batch 抽取按 doc sha1 判变，变了才重抽（防 39 篇全量重抽） |
| 对账辅助 | SQLite snapshots | 判断"某文件建过图吗"→ 归因缺向量/缺图 |

**写路径（对齐的保证）**：
```
① 写 Memgraph（MERGE 实体/关系，真相）
② 对新增/变更节点调 kg_bridge（business_id → upsert 向量 point，投影）
③ 更新 SQLite 账本（sha1/mtime/已抽取标记，状态）
```
任一步失败：图已写 → 下次 reconcile 补向量；账本未更 → 下次 build 重扫，天然幂等。
删除路径：先删向量 point（按 business_id）→ 删图节点 → 更账本。

**定期 reconcile（cron，可选）**：图 vs 向量对账 → 有图无向量自动补 bridge → 孤儿删 → 账本校正。

## 9. 风险

| 风险 | 缓解 |
|------|------|
| .hermes 补 15.9 万向量成本 | 先确认是否需检索，可只补 Class/文档级 |

| SQLite 账本与图不一致 | 账本只影响增量效率不影响知识正确性；reconcile 定期校正 |
| LLM 抽取质量波动 | R1-8B 实测 936 实体 0 缺陷；白名单+归一化兜底 |
