模式2（并行召回+智能融合）明显更好。

理由很简单：

1. 容错性：任何一路失败不影响整体，当前模式向量挂了就全挂
2. 适应性：不同查询自动路由到最合适的通道组合，而非一刀切
3. 充分利用图谱：图查询成为核心能力而非装饰品
4. 可扩展：新增查询类型只需加模板，不用改核心逻辑



复杂查询实例：完整工作流程

查询："修改 MySQL 数据库连接池配置会影响哪些服务？它们的调用链路是什么？"

这是一个影响面分析 + 路径查询的复杂场景，需要图谱+向量深度配合。



阶段 0：查询预处理

输入：原始查询字符串

工作节点：
1. 关键词提取器
   - 输入：完整查询
   - 提取：["MySQL", "数据库", "连接池", "配置", "影响", "服务", "调用链路"]
   - 识别核心实体：MySQL / 连接池配置
   - 识别意图词：影响（反向依赖）、调用链路（路径查询）

2. 意图分类器
   - 分析关键词组合
   - 检测到 影响 + 服务 → ImpactAnalysis（影响面分析）
   - 检测到 调用链路 → PathQuery（路径查询）
   - 最终判定：混合意图（ImpactAnalysis 主 + PathQuery 辅）

3. 实体识别
   - 候选实体：MySQL、数据库连接池配置
   - 规范化：MySQL → 图谱中的标准实体名（可能是 mysql-master、user-db 等）



阶段 1：四路并行召回（同时发起）

通道 1：向量召回

节点：Vector Channel

执行：
1. 查询向量化
   - 调用 Embed 服务：embed("修改 MySQL 数据库连接池配置会影响哪些服务？它们的调用链路是什么？")
   - 生成 1536 维向量：[0.023, -0.145, 0.089, ...]

2. Qdrant 检索
   - Collection: kg_nodes（知识节点集合）
   - 执行：余弦相似度搜索，top-30
   - 过滤条件：project = "digital-twin-v2"（如果指定）

3. 原始结果（假设返回）：
   
   1. [0.82] Entity: mysql-master (Database, "MySQL主库配置")
   2. [0.78] Knowledge: 数据库连接池优化 (经验)
   3. [0.76] Entity: connection-pool-config (Config, "连接池参数")
   4. [0.73] Entity: redis-cluster (Database) ← 语义漂移
   5. [0.71] Knowledge: 服务依赖治理 (经验)
   ...
   30. [0.52] Entity: UserService (Service)
   

输出：30个种子节点 + 语义分数



通道 2：关键词精确召回

节点：Keyword Channel

执行：
1. Cypher 构造
   cypher
   UNWIND ["MySQL", "连接池", "配置"] AS kw
   MATCH (n)
   WHERE n.name CONTAINS kw 
      OR ANY(k IN n.keywords WHERE k CONTAINS kw)
   RETURN DISTINCT n, elementId(n), 
          CASE 
            WHEN n.name = kw THEN 0.95      // 精确匹配
            WHEN n.name CONTAINS kw THEN 0.85  // 前缀匹配
            ELSE 0.75                        // 关键词匹配
          END AS match_score
   LIMIT 20
   

2. Memgraph 执行
   - 全图扫描节点属性
   - 匹配 name 和 keywords 字段

3. 原始结果：
   
   1. [0.95] mysql-master (精确命中 "MySQL")
   2. [0.95] mysql-slave (精确命中 "MySQL")
   3. [0.85] connection-pool-config (包含 "连接池")
   4. [0.85] db-config-center (包含 "配置")
   5. [0.75] mysql-monitor-service (关键词命中)
   

输出：20个精确匹配节点 + 匹配度分数



通道 3：图查询通道（核心）

节点：Graph Query Channel

执行：

子步骤 3.1：实体定位
cypher
// 先精确定位目标实体
MATCH (target)
WHERE target.name CONTAINS "MySQL" 
   OR target.entity_id = "mysql-master"
RETURN target, elementId(target)
LIMIT 1

结果：锁定实体 mysql-master

子步骤 3.2：影响面分析（反向依赖遍历）
cypher
MATCH (target {entity_id: "mysql-master"})
MATCH path = (affected)-[:DEPENDS_ON|USES|READS_FROM*1..3]->(target)
WHERE affected:Service OR affected:Application
RETURN DISTINCT 
       affected.entity_id AS service_id,
       affected.name AS service_name,
       length(path) AS distance,
       [rel IN relationships(path) | rel.type] AS rel_chain,
       [rel IN relationships(path) | rel.confidence] AS confidence_chain
ORDER BY distance ASC
LIMIT 50


原始结果：

1. UserService → DEPENDS_ON → mysql-master (distance=1, confidence=0.9)
2. OrderService → DEPENDS_ON → mysql-master (distance=1, confidence=0.95)
3. PaymentService → USES → mysql-master (distance=1, confidence=0.85)
4. ApiGateway → ROUTES_TO → UserService → DEPENDS_ON → mysql-master (distance=2)
5. NotificationWorker → READS_FROM → OrderService → DEPENDS_ON → mysql-master (distance=2)
...


子步骤 3.3：调用链路提取（每个受影响服务）
cypher
// 对每个受影响服务，提取其完整依赖子图
UNWIND ["UserService", "OrderService", "PaymentService"] AS svc
MATCH (s:Service {name: svc})
MATCH path = (s)-[:DEPENDS_ON|CALLS|ROUTES_TO*1..2]->(dep)
RETURN s.name AS service,
       [n IN nodes(path) | {id: n.entity_id, name: n.name, type: labels(n)[0]}] AS call_path,
       [r IN relationships(path) | {type: r.type, confidence: r.confidence}] AS relations


原始结果：

UserService 调用链：
  UserService → CALLS → AuthService
  UserService → DEPENDS_ON → mysql-master
  UserService → DEPENDS_ON → redis-session

OrderService 调用链：
  OrderService → CALLS → InventoryService
  OrderService → CALLS → PaymentService → USES → mysql-master
  OrderService → DEPENDS_ON → mysql-master
  OrderService → DEPENDS_ON → kafka-order-topic


输出：
- 50 个受影响服务节点
- 每个服务的依赖路径
- 关系类型和置信度



通道 4：混合通道（GraphRAG）

节点：Hybrid Channel

执行：
1. 复用向量召回的种子（前面通道1的结果）
2. 图扩展：
   cypher
   UNWIND $seeds AS seed
   MATCH (s {entity_id: seed})
   OPTIONAL MATCH (s)-[:SAME_AS]-(alias)
   WITH collect(s) + collect(alias) AS nodes
   UNWIND nodes AS n
   OPTIONAL MATCH path = (n)-[:RELATES*1..2]-(neighbor)
   RETURN n, neighbor, relationships(path) AS edges
   

3. 扩展结果：
   
   mysql-master 的邻居：
     → connection-pool-config (HAS_CONFIG, confidence=1.0)
     → db-monitor-service (MONITORS, confidence=0.8)
     → mysql-slave (REPLICATES_FROM, confidence=0.95)
   
   UserService 的邻居：
     → UserController (IMPLEMENTS, confidence=1.0)
     → AuthService (CALLS, confidence=0.9)
   

输出：种子节点 + 1-2跳邻居（约100个候选）



阶段 2：召回结果预处理

节点：Result Preprocessor

执行：
1. 去重：
   - 四路结果按 entity_id 合并
   - 保留每个实体的最高分数来源

2. 来源标注：
   
   mysql-master:
     - vector: 0.82
     - keyword: 0.95
     - graph: 1.0 (精确命中)
   
   UserService:
     - vector: 0.52
     - graph: 0.9 (影响面命中)
   

3. 关系挂接：
   - 把图查询返回的边信息附加到节点上
   - UserService 携带：DEPENDS_ON → mysql-master (confidence=0.9)

输出：120 个唯一候选节点 + 多源分数 + 关系元数据



阶段 3：智能融合与排序

节点：Fusion Engine

执行：

子步骤 3.1：意图加权
根据查询意图 ImpactAnalysis 设定权重：

graph_query_weight = 0.7   // 影响面分析靠图谱
vector_weight = 0.2        // 语义补充
keyword_weight = 0.1       // 精确匹配辅助


子步骤 3.2：分数融合
对每个候选节点计算最终分：

mysql-master:
  final_score = 0.7 × 1.0 (graph) + 0.2 × 0.82 (vector) + 0.1 × 0.95 (keyword)
              = 0.7 + 0.164 + 0.095 = 0.959

UserService:
  final_score = 0.7 × 0.9 (graph, 1跳依赖) + 0.2 × 0.52 (vector)
              = 0.63 + 0.104 = 0.734

OrderService:
  final_score = 0.7 × 0.95 (graph, 1跳依赖) + 0.2 × 0.68 (vector)
              = 0.665 + 0.136 = 0.801


子步骤 3.3：分桶截断
按 hop 距离分桶（优先近距离依赖）：

Bucket 0 (目标实体):
  - mysql-master (0.959)
  - connection-pool-config (0.887)

Bucket 1 (直接依赖，1跳):
  - OrderService (0.801)
  - UserService (0.734)

Bucket 2 (间接依赖，2跳):

每桶保留 top-15，总共约 45 个候选

关键观察点

1. 图查询通道起了决定性作用：
   - 精确定位 mysql-master
   - 反向遍历找到所有依赖服务
   - 提取调用链路

2. 向量召回是补充：
   - 提供语义相关的知识节点（"数据库连接池优化"经验）
   - 发现向量漂移噪声（redis-cluster），被 rerank 淘汰

3. 关键词召回是保险：
   - 保证精确实体不漏（即使向量失败）

4. 融合权重体现意图：
   - 影响面分析场景，图查询权重 0.7
   - 如果是语义探索（"如何优化性能"），向量权重会提到 0.6

5. 每一步都有降级路径：
   - Rerank 失败 → 用融合分数
   - 图扩展失败 → 仅用向量+关键词
   - 向量失败 → 图查询+关键词仍能工作

这就是为什么模式2完胜当前模式：图谱和向量各司其职，互为补充，任何一路失败都不影响整体。
